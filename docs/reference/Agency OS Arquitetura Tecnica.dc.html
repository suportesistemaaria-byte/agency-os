01Resumo e decisões

Monólito modular em TypeScript: um único app Next.js com domínios isolados, um PostgreSQL com isolamento por workspace, eventos internos gravados no banco (outbox) e processados por uma fila gerenciada. Sem microserviços no MVP. O app nativo (Expo) fica preparado, mas fora do caminho crítico.

Uma aplicação, vários domínios
CRM, Clientes, Operação, Conteúdo, Financeiro etc. são módulos com fronteiras claras dentro do mesmo deploy. Separar depois é possível; juntar microserviços prematuros não é.
Banco é a fonte da verdade
PostgreSQL com workspace_id em toda tabela de negócio e Row Level Security como segunda barreira.
Tudo vira evento
Cada ação importante grava um evento na mesma transação. Automações, notificações, auditoria e analytics consomem esses eventos, e nenhum módulo envia mensagem direto.
SLA em um só lugar
Uma biblioteca pura (@aos/sla) calcula prazos, com testes de tabela. Nenhum módulo calcula prazo por conta própria.
Arquivos fora do banco
Object storage compatível com S3, upload direto do navegador com URL assinada, thumbnails gerados em background.
Custo inicial baixo
Estimativa de US$ 90 a 160 por mês na fase 1, crescendo por uso, sem servidor próprio para manter.
02Stack recomendada

04Multi-tenancy

Modelo: banco compartilhado, isolamento por linha. É o mais barato e o que permite virar SaaS sem migração de dados.

Toda tabela de negócio tem workspace_id NOT NULL e as chaves estrangeiras são compostas (workspace_id, id): é impossível ligar um registro a outro de workspace diferente, mesmo por bug.
Índices e unicidades sempre começam por workspace_id (ex.: UNIQUE (workspace_id, slug)).
Cada requisição abre transação com SET LOCAL app.workspace_id e app.user_id; as políticas RLS filtram por esses valores. O serviço também filtra: são duas barreiras independentes.
O usuário do banco usado pela aplicação não tem BYPASSRLS. Só migrações e jobs administrativos usam outro papel.
Arquivos com prefixo do workspace; a URL assinada só é emitida depois da checagem de permissão.
Eventos, jobs, notificações e logs carregam workspace_id.
Usuário de portal é ligado a client_contact, e a RLS adicional limita a client_id dele.
Testes automáticos de isolamento: para cada rota, um usuário do workspace B tenta ler e escrever dados de A e precisa falhar.
-- exemplo de política
ALTER TABLE tasks ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON tasks
  USING (workspace_id = current_setting('app.workspace_id')::uuid)
  WITH CHECK (workspace_id = current_setting('app.workspace_id')::uuid);
05Usuários e permissões (RBAC)

Cargos são pacotes de permissões, não regras fixas. Um membro pode ter vários cargos; exceções individuais são possíveis; cada permissão tem um escopo.

Permissão
Formato modulo.acao. Ex.: clientes.view, clientes.edit, financeiro.view, financeiro.edit, comercial.view, comercial.edit, conteudo.create, conteudo.approve, tasks.edit, reports.view, sla.override, members.manage, audit.view.
Escopo
all (tudo do workspace), team (clientes em que está na equipe), own (só o que é seu). Ex.: Designer tem tasks.edit:own e conteudo.view:team.
Cálculo
permissões efetivas = união dos cargos + concessões individuais − negações individuais. Cache por sessão, invalidado quando muda.
Cliente (portal)
Não usa cargos internos. Cada client_contact tem flags: visualizar, comentar, solicitar, aprovar, recebe financeiro, recebe notificações.

07Conversão Oportunidade → Cliente

Um único comando de domínio (crm.convertOpportunity), executado em uma transação. Se qualquer passo falhar, nada é gravado. É idempotente: repetir a chamada devolve o mesmo cliente.

convertOpportunity({ opportunityId, idempotencyKey, missingData, team, onboardingTemplateId })

BEGIN
  1. trava a oportunidade (SELECT … FOR UPDATE); exige state = won e proposta aceita
  2. se já existe clients.opportunity_id = id → retorna o cliente (idempotência)
  3. reaproveita organization_id e people já existentes do lead (sem recadastro)
     completa só o que falta (razão social, CNPJ, endereço)
  4. INSERT clients (status = onboarding, opportunity_id, origem preservada)
  5. INSERT client_contacts a partir das people, com flags padrão
  6. INSERT contracts + contract_items a partir da proposta aceita
     (status = pending_finance_confirmation)
  7. INSERT client_team (funções → membros padrão)
  8. INSERT client_onboardings + onboarding_steps a partir do template
  9. UPDATE opportunities SET converted_client_id, converted_at
 10. INSERT audit_logs (opportunity.converted, before/after)
 11. INSERT domain_events: opportunity.converted, client.created,
     contract.created, onboarding.started
COMMIT

depois do commit (via eventos):
  · contract.confirmed (pelo Financeiro) → gera invoices (setup + recorrência)
  · onboarding.started → tarefas com SLA + convite do portal + aviso à equipe

A timeline do cliente mostra a da oportunidade (atividades, reuniões, propostas) porque ambas apontam para a mesma organization. Nada é copiado.

Para aprovarFaturas só são geradas após o Financeiro confirmar o contrato (decisão pendente desde a v2). Se preferir gerar na hora, basta trocar a regra de automação, sem mudar a estrutura.
08Engine de SLA

Biblioteca pura @aos/sla, sem acesso a banco: recebe tudo por parâmetro e devolve o resultado. É usada pela API, pelos jobs e pela tela (para o contador “restam 3h20”). Coberta por testes de tabela com os exemplos abaixo.

type Calendar = { timezone: 'America/Sao_Paulo',
                 periods: { mon..fri: [['10:00','13:00'], ['14:00','19:00']] },
                 holidays: Date[] }
type Policy   = { model: 'business_days' | 'business_hours', amount: number,
                 rule: 'A1_same_time', nearDueRatio: 0.25 }
type Interval = { start: Date, end?: Date, kind: 'client' | 'blocked' }

calculateDueAt({ calendar, policy, createdAt, pausedIntervals, now })
  → { startAt, dueAt, remainingBusinessMinutes, consumedBusinessMinutes,
      status: 'ON_TIME' | 'NEAR_DUE' | 'OVERDUE' | 'PAUSED' | 'BLOCKED' }
Regras
Início normalizado: se a solicitação chega fora do expediente (noite, almoço, fim de semana, feriado), o relógio começa no próximo instante útil.
Dias úteis (A1): vencimento = mesmo horário do início normalizado, N dias úteis depois. Se esse horário cair no almoço, vale o fim do período anterior (13:00).
Horas úteis: soma N × 60 minutos úteis, pulando almoço, noites, fins de semana e feriados.
Pausa (aguardando cliente) e bloqueio: durante o intervalo o relógio para. Ao retomar, o saldo restante em minutos úteis é somado a partir da retomada.
Status: NEAR_DUE quando o restante for ≤ 25% do total ou ≤ 2 horas úteis; PAUSED/BLOCKED enquanto houver intervalo aberto; OVERDUE quando now > dueAt.
Snapshot: o relógio guarda a política usada. Mudar a política depois não altera prazos já em andamento.
Mudança manual: só com sla.override, motivo obrigatório e registro na auditoria.

Para aprovarDepois de uma pausa, o vencimento deixa de ser “o mesmo horário”, porque o saldo é contado em minutos úteis (veja o caso “Pausa”). É a forma justa de não penalizar a agência nem o cliente. Confirme essa regra antes da implementação.

18Performance
Listas (tarefas, leads, clientes, faturas): paginação por cursor (due_at, id); 50 itens por vez; filtros sempre indexados.
Kanban (pipeline e conteúdos): carrega contagens e somas por coluna em uma query agregada e os cards por coluna sob demanda (20 + “ver mais”); movimento otimista com rollback.
Calendário: busca só a janela visível (mês ± 7 dias), com campos mínimos.
Dashboards: queries agregadas com índices; materialização diária (views materializadas atualizadas por job) para MRR, funil e Health score; cache de 60 s no Redis para KPIs.
Hoje: uma rota que agrega 5 queries em paralelo por usuário, todas indexadas por responsável e vencimento.
Imagens: sempre o thumbnail na lista; original só no detalhe; loading=lazy.
Vídeos: poster na lista; prévia curta no detalhe; original sob demanda.
Meta: respostas de API p95 < 300 ms; interação no Kanban < 100 ms percebidos.
